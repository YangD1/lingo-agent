# 0014 · AI 用量公示：功能点的 AI 标记与 token 估计

- **状态**：已采纳（2026-09-30；Q22a–Q22c 由用户确认）
- **日期**：2026-09-30
- **影响**：新增 `backend/app/usage/features.yaml`（功能 → 模型调用清单）和 `GET /usage/estimates`；前端新增 `AiBadge`；CLAUDE.md 架构约束加一条；`docs/agent-tools.md` 加一节。

## 背景
P1 实测后用户提出：凡是消耗模型 token 的功能都要让学习者看得出来，并且知道大概用了多少。模型 key 由租户自己配置、自己付费（ADR 0004），学习者点一个按钮之前应该知道它会不会花钱、花在哪。这也是开源项目的一个卖点：不把 AI 调用藏在界面后面。

已有的基础：每次模型调用都记在 `llm_usage`（ADR 0005，只有 task、连接、模型、输入 / 输出 token、ASR 的音频秒数，不存内容、不存价格）；ADR 0013 的活动公示已经说明了一轮对话里私教做了什么，但那是事后的，而且不给数量。

## 决定

### 1. 标记什么
每个会触发模型调用的入口旁边放一个小“AI”标。悬停、键盘聚焦或触屏点按都会弹出说明（Base UI Popover 的 `openOnHover`；Tooltip 在触屏上点不开，所以不用）。弹层逐条列出这个入口触发的调用：

- 做什么（回复、复盘这一轮、识图、语音转写……）；
- 立即调用还是回复后在后台调用；
- 每次约多少输入 / 输出 token；ASR 按音频秒数计费，显示秒数；识图、扫描页按“每张 / 每页”；
- 数字的来源：“按你最近 N 次调用的平均”或“还没有记录，这是默认估计”；
- 当前会用的模型（`连接:模型`），没配置时写“还没配置模型”。

只显示 token，不显示价格（Q22a）：各家价格和币种不同、经常变，而且 ADR 0005 已经决定不在库里存价格。

### 2. 清单放在后端配置里
`backend/app/usage/features.yaml` 列出每个功能对应的调用：`llm_usage` 里的 task 标签、provider 分区、实际走的路由（练习开场记为 `practice_opening`，走 `chat` 路由）、时机、单位、没有历史时的默认估计。`features.py` 严格校验（多余字段报错；ASR 必须且只有 ASR 带 `audio_seconds`）。

放在后端而不是写死在前端，是因为估计值要和 `llm_usage` 的 task 对齐，默认值是部署方可以调的数字，和 `adaptive/rules.yaml` 同理。

### 3. 估计值怎么算（Q22b）
`GET /usage/estimates`（登录即可访问，按租户隔离）：每个 task 取本租户最近 `window`（20）次成功、且厂商上报了用量的调用求平均；ASR 取上报了音频秒数的调用。没有样本就用清单里的默认值，并标明 `source=default`。按租户而不是按用户算：同一租户用同一套模型，样本多一些；返回的只是平均数，不泄露个人数据。

向量化调用（`embedding/memory`）不经过 LangChain 的 chat 回调，不写 `llm_usage`，所以始终用默认值（`history: false`）。

前端整站共用一次请求，缓存 5 分钟；第一次打开弹层时才请求，失败不缓存。

### 4. 规则
- **新增消耗模型的功能，必须在 `features.yaml` 登记，并在入口挂 `AiBadge`**（写进 CLAUDE.md 架构约束）。
- 例外：设置页的“测试连接”不挂。它只给租户管理员用，每次几个 token，而且测的是指定连接，不走路由，估计值没有意义。

## 取舍
- 平均值只是估计：对话越长，回复的输入 token 越多，前几轮会被高估、后面会被低估。弹层写明是平均，不承诺精确。
- 按 task 求平均而不区分模型：换了模型之后，前 20 次内的估计会混着新旧模型。换来的是实现简单，而且同一 task 换模型后 prompt 大体不变，输入 token 差别不大。
- 反思在后台每轮都跑，但每隔几轮还会额外重写会话摘要（同一个 `reflect` task），平均值里已经包含了这部分。

## 后果
- 学习者在点之前就能看到 AI 会被怎么用、大概用多少，和 ADR 0013 的事后公示互补。
- P4 的用量 / 成本看板可以复用 `features.yaml` 的功能分组。
