# 0018 · 朗读的三层方案：浏览器挑好声音、单词发音预生成、可选服务端朗读

- **状态**：已采纳（2026-10-01；Q25a–Q25f 由用户确认，全部按推荐）
- **日期**：2026-10-01
- **影响**：修订 ADR 0017 §5（浏览器朗读改为“挑声音 + 按句切分 + 学习者可调”）；PLAN 里语音 provider 的配置（`speech.tts: local_kokoro / edge_tts`）改为“浏览器优先，服务端朗读是租户可选的连接”；新增前端 `lib/speech.ts` 的声音挑选和朗读设置；25.4、25.5 落地时再新增 provider 层 `tts` 任务、音频缓存表和单词发音预生成任务。

## 背景
- ADR 0017 §5 的朗读只设置了 `utterance.lang`（`zh-CN` / `en-US`），声音交给浏览器默认。实测时很多设备的默认声音是最老的本地合成音（比如 Windows 的 Microsoft Huihui / David、Chrome 在 Linux 上的 eSpeak），听起来很机械。同一台设备上其实往往有好得多的声音（Edge 的 Natural 在线声音、Chrome 的 Google 声音、macOS 的 Premium / Enhanced 声音），只是没被选中。
- Chrome 的在线声音读长句会在大约 15 秒处截断；中文段和英文段分别由不同性别的声音读，也很突兀。
- 调研过自己跑朗读模型（详见看板任务 25 的调研记录）：
  - mlx-audio 只支持 Apple Silicon，不能上 Linux 服务器。
  - MOSS-TTS-Nano（0.1B，ONNX CPU）内存峰值约 2GB，4 核容器的总吞吐约每秒 1.7 秒音频；换算到 4 vCPU 云主机不到每秒 1 秒音频，两个人同时点朗读就要各等一倍，还会和后端抢 CPU。
  - 结论：线上服务器配置很低（ADR 0001），多用户场景自己跑模型撑不住。
- edge-tts 声音好、免费，但走的是非官方接口，随时可能失效，条款也不允许作为服务对外提供。

用户已确认：
- Q25a：声音和语速设置存在当前浏览器，不进画像。每台设备上可用的声音不同，存到服务器上换一台设备也用不了。
- Q25b：英文口音默认美音，可以选英音。
- Q25c：英文默认语速 0.9，可在 0.6–1.2 之间调。
- Q25d：edge-tts 不内置。
- Q25e：预生成的单词发音由部署方用自己配置的朗读服务生成，存在部署方自己的库里，不进仓库。
- Q25f：第 2、3 层（单词发音预生成、服务端朗读）等任务 24 实测和第 1 层上线以后再决定做不做。
- MOSS-TTS-Nano 不作为方案，只在文档里留一条建议：有闲置算力或显卡的自部署可以用，外面包一层兼容 OpenAI 的 `/audio/speech` 接口，按第 3 层接入。

## 决定

三层，从免费到付费，前一层不够用时才往下走：

| 层 | 内容 | 花费 | 何时做 |
|---|---|---|---|
| 1 | 浏览器 `speechSynthesis`，但自己挑声音、切句子，学习者可以调 | 免费，不经过服务器 | 现在（25.2、25.3） |
| 2 | 单词发音预生成：用第 3 层的服务按词书批量生成，缓存后反复用 | 一次性，几十 MB | 25.5，按 Q25f 再定 |
| 3 | 服务端朗读：租户配置的朗读连接，配了就优先用，失败退回浏览器 | 按字符计费 | 25.4，按 Q25f 再定 |

### 1. 浏览器挑声音（`lib/speech.ts`，纯函数）
- **等 `voiceschanged`**：Chrome 的声音列表是异步加载的，`getVoices()` 第一次常常是空的。挑声音要在列表到齐之后，到齐后缓存结果，列表再变化时重新挑。
- **按语言筛**：
  - 中文：`zh-CN` > `zh-TW` > 其他 `zh`。排除 `zh-HK` 和 `yue`（粤语，用普通话的拼读规则读不对）。
  - 英文：学习者选的口音（`en-US` 或 `en-GB`）> 其他 `en`。
  - 语言标签统一按小写、`_` 换成 `-` 比较（Android 上有 `en_US` 这种写法）。
- **按质量打分**，同语言内取最高分：
  - 加分：名字含 `Natural` / `Neural`（Edge、Windows 11 的在线神经声音），`Premium` / `Enhanced`（macOS、iOS 下载的高质量声音），`Google`（Chrome 的在线声音），`localService === false`（在线声音一般比本地的好）。
  - 排除：macOS 的趣味声音（Albert、Bad News、Bells、Boing、Bubbles、Cellos、Jester、Organ、Superstar、Trinoids、Whisper、Zarvox 等，按名字表）。
  - 减分：Eloquence 系列（Eddy、Flo、Grandma、Grandpa、Reed、Rocko、Sandy、Shelley），以及 eSpeak。
  - 分数相同时按浏览器给的顺序（`default` 为真的优先）。
- **整段一个声音**：如果最高分的声音名字含 `Multilingual`（Edge 的多语言神经声音），中英文都用它读，不再切换声音。
- **中英尽量同性别**：Web Speech API 不提供声音性别，用一张常见声音的性别表（Microsoft、Google、Apple 的常见声音名）。先挑英文声音，再挑中文声音：语言档次和质量分相同时，优先选和英文声音同性别的（不会为了同性别换一个更差的声音）；查不到性别时不做限制。学习者手动选过的声音优先于自动挑选，在这台设备上已经不存在时按自动处理。
- **按句切短**：每一段再按句末标点（`。？！；;` 和换行，以及后面跟空格的 `.?!`，所以 `3.5` 不会被切开）切成句子，单句超过约 200 个字符时再按逗号切。每句一个 utterance 依次读，避免 Chrome 在线声音读长句被截断。
- **没有中文声音时**：只读英文段，并提示一次“这台设备没有中文朗读声音，只读英文部分”。没有英文声音时不显示朗读按钮（等同于不支持）。浏览器还没给出声音列表（或者从来不给）时，只按语言设置 `lang`，交给浏览器自己选声音（即原来的做法）。
- **语速**：英文按学习者的设置（默认 0.9），中文固定 1.0。
- **在线声音播不出时退回本地声音**（2026-10-01 实测补充，任务 25.7）：Edge 的 Online (Natural) 声音要连微软的语音服务，Chrome 的 Google 声音要连 Google；连不上时浏览器照样列出这些声音，但读的时候没有声音（Edge 自己的“大声朗读”也一样）。另外 Edge 150 有已知问题，会把在线声音列成 `Microsoft undefined Online (Natural) - undefined`。处理办法：
  - 名字里带 `undefined` 的声音直接排除。
  - 所有句子一起排进浏览器队列，同时逐句盯着：轮到一个在线声音（`localService === false`）的句子时开始计时，3 秒内没有 `onstart`，或者没开始就 `onend` / `onerror`，就判定这个声音在这台设备上播不出声。
  - 判定后取消队列，被判定的声音不再参与挑选，从出问题的那一句开始，用剩下的声音重新排队（`revoice()`：同语言重新挑；没有声音可用的语言跳过）。学习者手动选的声音也一样。
  - 判定只在当前页面有效（Q25g），刷新后重新尝试，因为换网络或开代理后可能就能用了。
  - 本页第一次退回时，在那条私教回复下提示一次；设置面板里被判定的声音标为“（这台设备上播不出声）”，“自动（当前：…）”也会跟着变。
  - 本地声音不计时，读得慢也不算失败；在线声音已经开始读了，读多久都不算失败。
- 都是纯函数（输入声音列表和设置，输出挑中的声音和 utterance 列表），用各平台的模拟声音列表（Windows Edge、Windows Chrome、macOS Safari、macOS Chrome、Android Chrome、Linux Chrome）做单测。

### 2. 朗读设置（前端，存在当前浏览器）
- 设置项：中文声音、英文声音（下拉，默认“自动（当前：<挑中的声音名>）”，下拉里只列当前语言的可用声音）、试听、英文口音（美音 / 英音，默认美音）、英文语速（0.6–1.2，默认 0.9；中文语速固定 1.0）。
- 存在 `localStorage`，读写都包在 try/catch 里，读不到就用默认值；选中的声音在这台设备上已经不存在时，按“自动”处理。
- 不进画像，不经过后端（Q25a）。
- 单词气泡、私教气泡的朗读、背单词页共用同一份设置和同一个 `speak` 入口。
- 入口：私教气泡朗读按钮旁的小齿轮，和设置页的“朗读”一栏，打开的是同一个面板。
- 第 1 层不调用模型、不经过后端，所以不登记 `features.yaml`，不挂 `AiBadge`（与 ADR 0017 §5 相同）。

### 3. 服务端朗读（可选连接，25.4）
- provider 层新增 `tts` 任务，和 ASR 一样走租户连接与路由，支持 fallback 链（ADR 0002、0004、0008）。支持两类：
  - 兼容 OpenAI 的 `POST /audio/speech`：OpenAI、硅基流动，以及自部署的 mlx-audio、Speaches、MOSS-TTS-Nano（包一层接口后）。
  - Azure 语音（SSML）：免费档每月 50 万字符，声音质量好，适合国内外都能访问的部署。
- 按“文本 + 声音 + 语速”的哈希缓存音频（按租户隔离），同一句话第二次读不再花钱；缓存有总量上限，超出按最久未用淘汰。
- `features.yaml` 登记（task `tts`，学习者点朗读时触发，按字符估算），朗读按钮旁挂 `AiBadge`。每次实际调用记入 `llm_usage`，缓存命中不记。
- 前端：租户配置了 `tts` 路由时，朗读优先请求后端；请求失败或超时，退回第 1 层的浏览器朗读，不报错打断。
- 不内置 edge-tts（Q25d）。部署方如果自己愿意承担风险，可以用社区的 edge-tts 兼容 OpenAI 接口的封装，按普通 `/audio/speech` 连接接入，仓库不提供也不推荐。
- 不在后端容器里跑朗读模型；本地模型只作为可选的独立容器（像 `make asr-up` 那样），文档里说明内存和 CPU 的实测数字。

### 4. 单词发音预生成（25.5）
- 用第 3 层配置的服务，按词书批量生成单词发音（美音、英音各一份），存在部署方自己的库里（Q25e）。音频不进仓库，也不随镜像分发。
- 后台任务，可断点续跑；开始前显示要生成的词数和预计字符数（以及按所配服务的单价估算的费用），运行中显示进度。
- 查词（单词气泡、背单词页）朗读时优先用缓存的发音；没有缓存时按第 3 层、再按第 1 层退回。

## 公示（ADR 0013、0014）
- 第 1 层不涉及模型调用，不需要公示。
- 第 3 层：`features.yaml` 新增 `read_aloud`（task `tts`），朗读按钮旁挂 `AiBadge`。它不是对话轮次里的工具调用，不写 `agent_activities`；在 `docs/agent-tools.md` 的“对话之外的调用”里补一行。
- 第 2 层：预生成是部署方发起的后台任务，在 `docs/agent-tools.md` 的后台任务里登记；学习者查词时用的是缓存，不产生调用。

## 取舍
- **浏览器优先而不是服务端优先**：大多数设备上其实有不错的声音，问题出在没挑。挑好声音零成本、零服务器内存；服务端朗读声音更统一，但每读一句都花钱，低配服务器也跑不动本地模型。
- **设置存在浏览器而不是画像**：声音是设备上的资源，换台设备就没有了；存到服务器反而会在别的设备上选中一个不存在的声音。代价是换设备要重新选，但“自动”已经能挑到这台设备上最好的。
- **用名字表判断质量和性别**：Web Speech API 不提供这些信息，只能按名字猜。名字表需要随浏览器更新维护，猜错的后果只是挑了个次好的声音，学习者也可以手动换。
- **不内置 edge-tts**：声音好又免费，但它是非官方接口，可能随时失效，开源项目内置它会把风险转给所有部署方。
- **第 2、3 层先设计后实现**：先看第 1 层上线后的效果，如果挑好声音已经够用，就不必为朗读引入付费调用和音频存储。
