# 0033 · 提示词版本与评估回归

- **状态**：已采纳（2026-10-13，任务 67、68；Q67a、Q68a–c 由用户确认，全部按推荐）
- **日期**：2026-10-13
- **影响**：**补充 ADR 0021 §2、§7**（选题：没有证据的语法点打折；“巩固中”的点进复习名额，`kc_mastery.gate_ready_at`，见 §6）；**补充 ADR 0005**（`llm_usage` 记每次调用用到的提示词版本）和 **ADR 0005 / 任务 36 的评估集**（加分数基线、回归对比、新评估集和模拟学习者）。新增 `llm_usage.prompts` 列、`backend/evals/baselines.json`、`make prompts`。

## 背景
- 提示词是 `backend/app/prompts/` 下的 41 个 `.md`，`load_prompt(name)` 读文件（带缓存），调用方再 `.replace("{占位符}", …)` 或拼接后放进消息。版本只靠 git。
- 评估集（任务 36、46.6、64.3）录制模型回复，键是“任务 + 消息 + 输出结构”的哈希；提示词一改，回放就对不上、失败并提示重录。回放结果是确定的，CI 的 pytest 已经在跑（`testpaths` 含 `evals`）。
- 缺的：
  1. 线上看不出某次调用用的是哪版提示词，改了提示词以后没法按版本比较错误率、token、后备率。
  2. 重录后分数变了没有记录：门槛只是下限，从 26/26 掉到 24/26 仍然“通过”，评审 PR 时看不到。
  3. 评估集只覆盖 critic、批改、诊断、口语小结；路由、记忆反思、写作批改、阅读 critic 没有。
  4. PLAN“验证方式”里“模拟学习者跑多轮、弱点被识别、掌握度上升”一直没有做。

## 决定

### 1. 提示词版本 = 内容哈希（Q67a）
- 每个提示词文件的版本是其内容（`load_prompt` 返回的去空白文本）SHA-256 的前 8 位十六进制。自动生成，不手写版本号，git 仍是唯一来源；**不做**数据库存提示词、在线编辑、回滚（开源部署方改提示词就是改文件、提 PR，评估集兜底）。
- `make prompts` 列出每个提示词的名字、版本、行数，方便和 `llm_usage` 对照。

### 2. 一次调用用了哪些提示词：按内容识别，不改调用方
- 调用方拿到提示词后会替换占位符、拼接、再包成消息，40 多处调用点各不相同；让每处都显式传版本，改动面大，漏一处就记错。用 contextvar 记“本次请求读过哪些提示词”也不准：一次聊天先路由、再回复，读过的提示词会混在一起，而且 `load_prompt` 有缓存、可能在别的时机读。
- 做法：启动时把每个提示词按 `{占位符}` 切开，取最长的一段字面文本作为**指纹**（现有 41 个提示词的指纹最短 127 个字符，单测保证每个都能被识别、互不包含）。`UsageRecorder.on_chat_model_start` 把这次调用所有消息的文本拼起来，看哪些指纹出现在里面，就记下 `{名字: 版本}`。41 次子串查找，纯 CPU，微秒级，符合 recorder“只做 CPU 工作、内联执行”的要求。
- 记在 `llm_usage.prompts`（JSONB，可空；没识别出任何提示词时为空）。只记名字和版本，**仍然不记提示词或回复内容**（ADR 0005）。
- 不认识的文本（用户输入、学习者上下文）不会被误认：指纹是整段的提示词原文，用户恰好粘贴一整段提示词的情况只会让这一行多记一个名字，只影响统计，可以接受。
- 实时通话（ADR 0030）的指令不走 LangChain，由中继在写用量时用同一个识别函数处理会话指令。
- OTel：Phoenix 里的 trace 已经带完整的提示词文本（OpenInference 记录消息），**不另加 span 属性**，免得依赖 OpenInference 的内部实现；按版本统计看 `llm_usage`。

### 3. 分数基线与回归（Q68b）
- `backend/evals/baselines.json`：每个评估集一项，记各指标的通过数 / 总数、录制所用模型、录制日期，以及这个评估集的请求里识别出的提示词版本（用 §2 的识别函数处理录制时的消息）。
- `--record` 重录时：报告逐项显示“基线 → 本次”和差值，然后把新分数写进基线。分数下降不阻止写入（模型波动是真实的，见诊断评估集 8/9 → 7/9 的记录），但会在报告里醒目标出；基线文件随 PR 提交，**评审在 diff 里看到分数变化**。
- 回放（CI、`make eval`）：除了门槛，还要求每项分数**等于**基线。录制不变时回放是确定的，不相等说明评估器代码或判分逻辑变了却没重录或没更新基线，直接失败。
- CI 不跑真模型（Q68b）：在 CI 放 key 违反“key 只在应用内由租户配置”（ADR 0004），费用也不可控。真模型由维护者改提示词时手动 `make eval-live --record`。CI 把分数表写进 GitHub Actions 的 job summary。

### 4. 新评估集（Q68a）
- `route`：给定对话片段，路由到哪个 coach 对不对（含该留在私教的闲聊、看似阅读其实在问语法等边界）。
- `reflect`：记忆反思该记的记了、不该记的（一次性的、模型自己说的）没记、敏感信息不记；语法标签用目录里的 id。
- `writing_review`：找出真错误（引用原文）、对的句子不乱改、语法点 id 在目录里。
- `reading_critic`：拒掉答案不在文中、不止一个对、超出文章的题，放过好题。
- 数据全部合成，不含真实用户数据；门槛写在数据集里（沿用任务 36 的 Q36c）；用真模型录制一次（需要维护者的 key，临时账号）。
- 私教回复质量（需要模型当裁判，成本高、结果波动大）这次不做。

### 5. 模拟学习者（Q68c）
- 确定性规则学习者：预设若干弱点语法点，对这些点按固定概率答错（错法按语法点给定），其余按高概率答对；用固定随机种子。
- 跑多轮“选题 → 出题（用固定题库代替模型生成）→ 作答 → 代码判分 → 证据 → BKT / Elo → 下一轮选题”，断言：预设弱点的掌握度低于其他点并被选题优先；练习中弱点的占比明显高于随机；弱点的答对率上升后（学习者按设定“学会”）掌握度随之上升。
- 不调模型，作为 pytest 跑在 CI 里；放在 `backend/evals/`（它衡量的是自适应引擎的行为，不是单个函数）。用 LLM 扮演学习者更像真人，但只能手动跑、结果不稳定，以后需要时再加。

### 6. 模拟学习者发现的两个选题问题（Q68d、Q68e，2026-10-13 用户确认按推荐）
第一次跑模拟学习者（B1，预设 3 个弱点，每天一套题，30 天）就发现两处与 ADR 0021 §2、§7 的设计意图不符：

1. **已知弱点被没练过的语法点挤掉**（Q68d）：选题优先级 = (1 − p) × 重要度 × 近期错误加权。一个有错误证据、练到 p = 0.69 的弱点约 0.52；而没有任何证据的 B1 点按先验 0.4 是 0.6、B2 点（先验 0.15 × 重要度 0.7）也约 0.6，这样的点五十多个，弱点要等它们轮完（模拟里 8 天）才回来，回来时又掉到 0.13。改法：**没有证据的语法点优先级乘 `practice.untested_factor`**，有证据的弱点先练，没有弱点时照样探索新点。取值 0.4 而不是讨论时举例的 0.6：有 2 次近期错误的弱点优先级是 (1 − p) × 1.5，没证据的 B1 点是 0.6 × 系数，系数 0.6 时弱点要低于 p ≈ 0.76 才赢，模拟里 p = 0.8 的弱点仍被搁置 11 天；0.4 时低于 p ≈ 0.84 就赢。剩下的取舍：BKT 被几次蒙对抬到 0.84–0.95 的点仍排在没证据的点后面，要等对话里再出错（近期错误加权）或没证据的点练完。
2. **掌握度冲高但没过门槛的点断档**（Q68e）：一天答对 4 次，p 从 0.12 到 0.99，但“已掌握”还要 3 种题型、跨 20 小时、14 天内对话无错（ADR 0021 §7）。它优先级≈0 选不到，又不是“已掌握”不进 FSRS 复习，于是再也不出现、永远过不了门槛。改法：p ≥ `bkt.mastered` 而未过门槛的点叫**巩固中**，`learned.progress` 算出门槛最早能满足的时间 `gate_ready_at`（首次答对 + `min_span_hours`、最近一次对话 / 写作错误 + `clean_days`，取较晚者），存进 `kc_mastery`；到时间后和已掌握的点**共用复习名额**（按到期时间排），换没过的题型出题，直到过门槛进入 FSRS。今日计划“没有弱点时练到期的复习”也算上到时间的巩固点。模拟里这类点很多（会的语法点答对一两次就到 0.95，30 天约 70 个），每套题 3 个复习名额按时间先后排队，最长等约 12 天；这是门槛设计（3 种题型、跨天）本来的成本，之前这些点是直接断档。

两处都改选题、不改掌握度的计算；`rules.yaml` 版本号随之更新，`kc_mastery` 按惯例重算（新列 `gate_ready_at` 由重算填上）。

## 取舍
- 指纹识别依赖“提示词原文的最长字面段会原样出现在消息里”。如果以后有调用方对提示词做了截断或改写，这次调用就识别不出那个提示词（只是少记，不会记错）。单测覆盖每个提示词都能被识别、指纹互不包含。
- 一个提示词改了，所有用到它的评估集回放都失败、需要重录；重录要真模型和费用。这是有意的：不允许拿旧答案评新提示词（任务 36 的 Q36a）。
- 基线要求回放分数“相等”而不是“不低于”：更严，但回放本来就是确定的，相等才能发现判分逻辑的无意改动。

- **§4 新评估集的实测发现**：模型常把用对的部分列成“错误”，改前改后一样。以前反思会把这些记成错误证据，拉低掌握度，写作批改也会显示出来。现在：
  - `reflection.tagged_evidence` 和 `writing.review.check` 在代码里丢掉这类条目，评估另报不设门槛的 `no_unchanged`。
  - 反思的错误还必须引用该条学习者消息里的原文。

  - 提示词收紧后，qwen-plus 仍会记下学习者明说的健康信息。这一项卡在 80% 门槛上，记为已知弱点，明细见 `backend/evals/README.md`。
- **录制不挑选**：真模型几轮运行之间波动明显（例如写作批改的错误找到率在 5/9 到 8/9 之间）。录制是一次运行的原样结果，基线记的就是这次。
