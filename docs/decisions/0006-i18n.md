# 0006 · 前端国际化（中英双语）

- **状态**：已采纳
- **日期**：2026-09-28

## 背景
P0 的界面就要支持英文和简体中文。项目开源，面向的用户母语各不相同；学习内容本身是英语，但界面、提示和错误信息要用用户熟悉的语言。需要决定：用什么库、语言放在 URL 里还是别处、默认语言怎么定、后端错误怎么本地化。

## 决定

### 1. 库：next-intl 4
- 4.14 的 peerDependencies 支持 Next 16。服务端组件用 `getTranslations`，客户端组件用 `useTranslations`。v4 的 `NextIntlClientProvider` 在服务端渲染时会自动继承 locale 和 messages，不用手动传。
- 通过 `global.ts` 扩展 `AppConfig`，文案的 key 带类型检查：写错 key 在 typecheck 阶段就会报错。

### 2. 不做 URL 语言前缀，语言存在 cookie 里
- 这是登录后使用的应用，不需要按语言做 SEO，所以 URL 里不带 `/en`、`/zh-CN` 这类前缀，路由结构保持简单。
- `src/i18n/request.ts` 的 `getRequestConfig` 按以下顺序确定语言：
  1. `NEXT_LOCALE` cookie，只在用户主动切换时写入，有效期一年；
  2. 请求头 `Accept-Language`（按 q 值排序，所有 `zh-*` 都归到 zh-CN，`en-*` 归到 en）；
  3. 默认 en。
- **与最初计划的差异**：原计划由 `proxy.ts` 在首次访问时检测语言并写 cookie。实现时改成每次请求在 `getRequestConfig` 里直接协商：用户没有主动选择之前一直跟随浏览器语言，`proxy.ts` 只负责鉴权，两件事互不影响。
- 切换语言：客户端组件调用 Server Action `setLocale` 写 cookie。Next 会在同一次往返里返回按新语言渲染的页面，不需要手动刷新。
- 语言协商逻辑写成纯函数（`negotiateLocale` / `resolveLocale`），有单测覆盖。

### 3. 文案文件
- `frontend/messages/en.json` 和 `zh-CN.json`，按页面或功能分命名空间（`home`、`errors`……）。
- 单测保证：两份文件的 key 完全一致，每个 key 用到的 ICU 占位符一致，并且没有空字符串。

### 4. 后端错误的本地化
- 后端所有错误统一为 `{detail: {code, message}}`（ADR 0003 §3）。前端的 `useErrorMessage()` 按 `errors.<code>` 查找文案，找不到时显示后端给的英文 message。
- 前端自己产生的错误（例如 `network_error`）也放在 `errors` 命名空间里。

## 取舍
- **cookie 与 URL 前缀的比较**：URL 前缀便于 SEO、方便分享指定语言的链接，但每个路由都要套一层 `[locale]` 段，还要引入 next-intl 的路由 proxy。本项目的页面几乎都要登录才能访问，这些好处用不上。以后如果要做公开的营销页，可以只给那部分页面加前缀。
- **next-intl 与自己写一个 context 的比较**：自己写大约 50 行就能实现取文案，但 ICU 复数和插值、日期和数字格式化、服务端组件支持、类型化的 key，都要重新实现一遍。next-intl 在 Next 生态里最常用，体积也可以接受。
- **中文变体**：P0 只有简体中文，繁体用户暂时也看简体。以后加 zh-TW 时，只需改 `matchTag` 并新增一份文案文件。
