# 0064 · 分段回复：快模型先答，私教自己决定要不要补一段深入分析

- **状态**：已采纳（2026-10-24，任务 124.1；方向、上限、Q124a–c 用户 2026-10-24 确认）
- **日期**：2026-10-24
- **影响**：**补充 ADR 0015 §1、§5**（tutor 子图多一个 `deepen` 节点、多一个工具 `continue_deeper`）、**ADR 0057**（先说话再调工具的提示词要兼容续写）、ADR 0013（新工具和后台步骤要公示）、ADR 0014（`chat_message` 多一种调用）。新路由 `chat_deep`；`tenants` 加一列续写设置（迁移）；SSE 多一种 activity 步骤和段落边界，旧客户端不受影响。

## 背景
自由对话里，同一个问题需要的深度差别很大：寒暄、简单问答几秒就该回完，而“为什么这里用现在完成时”“affect 和 effect 有什么区别”这种问题，用思考型模型才讲得透，但首字要等十几秒到几十秒。现在一个任务只能选一种：`chat` 路由配快模型，深问题讲得浅；配思考模型，每轮都慢。

对照 ChatGPT 的做法（2026-10-24 调研）：它的“分段”主要来自同一个模型写一段、调工具、再写一段（GPT-5 的 tool preamble，Responses API 用 `phase: commentary / final_answer` 区分中间说明和最终回答），加上路由先选快 / 慢模型、首字之前先流式显示思考摘要。“快模型先答、慢模型接着补”没有公开证据，但工程上可行。本项目已经有前两样（tutor ↔ tools 循环、ADR 0057 先说话再调工具、ADR 0013 的 activity 流），缺的是快慢接力。

产品要求（用户定）：第二段**由私教自己决定**，不做“讲详细点”之类让学习者手动要求的按钮；续写**必须有上限**，不能一直思考；上限**由租户自己设**，用来控制成本。

## 决定

### 1. 范围：只在自由对话的 tutor 上做
- 只有 tutor 子图有续写。grammar / writing / reading / speaking 各 coach、桌宠每天的开场（`daily_opening`）、计划开场、语音通话都不续写：coach 有自己的节奏，开场要短，语音要快。
- 作文本来就由 supervisor 转给 writing_coach，不在这里处理。

### 2. 第一段：沿用 `chat` 路由，只写有把握的部分（Q124b）
- 第一段还是现在的 tutor 调用，路由、流式、首字速度都不变。
- 提示词（`tutor_tools.md`）加一条：问题需要细讲时，先给直接的回应和有把握的结论，没把握的地方不下断言，留给后面的补充。宁可短，也不写错——学习者先记住的错误，后面再纠正效果很差。

### 3. 什么时候续写：规则 + 模型判断（Q124a、Q124c）
任一条件满足就续写（还要满足 §5 的上限）：

- **规则**（代码判断，不调模型）：
  - 学习者在追问原因或辨析：消息里有“为什么 / 区别 / 有什么不同 / why / difference / vs”等词；
  - 较长的语法提问：英文 15 个词以上、或中文 30 字以上，并且是问句；
  - 规则只看学习者这一条消息，词表放在代码常量里，124.7 实测后再调。
- **模型判断**：给 tutor 一个工具 `continue_deeper(reason)`。它觉得第一段不够，就在写完文字后调用它（和 ADR 0057 一样，先写话再调工具）。`reason` 只用于公示和记录，不进第二段的提示词——工具参数是模型生成的，按不可信数据对待（ADR 0013）。
- 只调了 `continue_deeper`、没写文字的回复：第一段就是空的，直接进第二段，不会比现在更慢。

### 4. 第二段：`chat_deep` 路由，只补充、不重复
- 新路由 `chat_deep`，dev / prod 预设默认用思考型模型，路由上的思考强度最高 `medium`（ADR 0047），租户可以在设置页改路由和兜底链，和其他任务一样。
- 输入：这一轮之前的对话、学习者这条消息、第一段原文。提示词要求：只写第一段没讲的部分，不重复；第一段有错就明确指出并改正，不悄悄换一种说法；不出卡片。
- 第二段**不绑卡片工具**。第二段要不要再续写见 §5。
- 第二段里如果有练习题（比如“试试这几句”），照样要先过 critic 才能给学习者；第一版的提示词直接要求第二段不出题，题目还是走 `give_quiz` 卡片。

### 5. 上限：租户在设置页自定义（用户定）
`tenants` 加一列 `deepen_settings`（JSONB，Pydantic 模型校验），设置页在 `chat_deep` 路由旁边：

| 设置 | 默认 | 范围 | 说明 |
|---|---|---|---|
| `enabled` | 开 | — | 关掉后不绑 `continue_deeper`，规则也不触发 |
| `max_segments` | 1 | 1–3 | 每轮最多续写几段；最后一段不绑 `continue_deeper`，由代码计数 |
| `first_chunk_seconds` | 15 | 5–60 | 第二段多久没出第一个字就放弃 |
| `total_seconds` | 60 | 10–300 | 第二段从开始算的总时长，到了就停 |
| `max_tokens` | 1500 | 256–8000 | 每段最多输出多少 token |

- 范围在接口校验，防止设成无限等待或无限长；只有租户管理员能改。
- 思考强度不重复设：沿用 `chat_deep` 路由上已有的 `reasoning` 参数。
- **固定的门槛，不开放**：最近 3 轮里已经续写过 2 轮，这一轮就只认规则，不认模型的 `continue_deeper`。防止模型每轮都觉得“还不够”。
- 学习者自己不能关（用户 2026-10-24 定：先不加，等有人嫌打扰再说）。
- 每日次数上限暂不做（用户定：以后再说）。

### 6. 超时、失败和取消：不打断这一轮
- 首字超时和总时长都由 `deepen` 节点自己计时（`asyncio.timeout`），和 ADR 0056 的“卡住判断”分开：0056 判断的是一次调用是不是挂住了，这里限的是学习者愿意等多久。`chat_deep` 没开 `resilient` 时，超时后不重试。
- 超时、报错、兜底链用完：这一段到此为止，**已经写出来的部分保留**（总时长到了时，前面流出来的字不收回，末尾标明“补充分析到时间了，没写完”）；首字前就失败的，不留空段（取消不在此列，见下面）。activity 显示“补充分析超时，已跳过”或“补充分析失败，已跳过”。第一段本来就是能单独成立的回答，所以这一轮照常结束。
- **离开对话**：和 ADR 0058 一样照常写完（仍受总时长限制），回来能看到。
- **第二段没写完时学习者发了新消息**：同一对话同一时间只有一个回复（会话锁，`chat/locks.py`），直接发会被拒（409）。所以续写中输入框照常可用，发送时前端先停掉这一轮（走 ADR 0003 断开取消的路径），再发新消息。第一段在 `deepen` 开始前已经存进 checkpoint，不受影响；第二段按 ADR 0003 的取消语义丢掉，前端把没写完的第二段换成一行“补充分析已停止”，刷新前后显示一致。
- 取消和超时处理不同：超时是 `deepen` 节点自己判断的，能把已写的部分存下来；取消是整个图被取消，节点来不及写状态，所以不存。
- 用量都记 `llm_usage`：第二段的 task 记 `chat_deep`，和 `chat`、`chat_tools` 分开，用量看板能单独看续写花了多少。

### 7. 怎么存、怎么显示
- 每一段存成一条独立的 `AIMessage`，`additional_kwargs` 带段落标记（`segment: "deep"`、第几段、终态 `done / timeout / failed / cancelled`）。checkpoint 里的消息顺序就是显示顺序。
- 历史接口（`to_chat_messages`）现在会把一轮里连续的 AI 消息合并成一条（ADR 0015 §5）。续写的段照样并进这一条回复，但要把段落边界带给前端（新增可选字段，旧客户端忽略它也能显示全文）。
- 前端在同一条回复里接着往下写，第二段前面有一个小标题“补充”；等待第二段时显示“还在深入分析… N 秒”，有思考摘要就流式显示。
- SSE：沿用现有事件，加一种 activity 步骤（`deepen`：started / done / timeout / failed / cancelled），第二段的文字照常作为消息块推送、带上段落标记。旧客户端会把两段当成一段连续显示，不会出错。
- `done.message_id` 取这一轮最后一条 AI 消息的 id，和 ADR 0057 一致。

### 8. 记忆和学习者模型
- 长期记忆抽取在整轮（含续写）结束之后跑，拿到的是合并后的内容；续写被取消时只有第一段。
- 第二段不直接改掌握度。对话里的语法证据照旧由现有的抽取流程处理，不因为续写多算一次。

### 9. 公示
- `docs/agent-tools.md` 加 `continue_deeper` 工具和 `deepen` 步骤；回复下“{名字}做了什么”一行显示“补充了一段深入分析（原因）”或超时 / 跳过。
- `features.yaml` 的 `chat_message` 加一条 `chat_deep` 调用：标明“只在部分回复里出现”，默认估计按 124.7 实测的触发率和平均 token 填。
- 聊天入口的 `AiBadge` 文案写明“有时会自动补充一段深入分析”。

## 取舍
- **不做“讲详细点”按钮**：把深度判断推给学习者，产品显得笨（用户定）。代价是触发全靠规则和模型判断，会有误触发和漏触发，靠 124.7 实测调规则。
- **不并行跑快慢两个模型**：两个同时跑能让第二段更早写完，但每轮都多花一次思考型调用，大部分轮次用不上；先写完第一段再决定，第二段只在需要时调用。代价是第二段要等第一段写完才开始。
- **第一段要保守**：换来的是少出现“先讲错、再纠正”。代价是需要细讲的问题，第一段读起来可能偏短。
- **上限交给租户，频率门槛写死**：租户自己控成本；频率门槛是防止模型失控的保护，开放出去容易被误关。
- **第二段不绑卡片工具**：避免两段各出一张卡片，也让第二段的行为好预测。代价是深入讲完之后想顺手给练习，要等下一轮。
- **超时保留已写部分而不是整段丢掉**：学习者已经看到了，收回反而更乱；末尾标明没写完。
