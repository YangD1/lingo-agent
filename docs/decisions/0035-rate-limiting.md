# 0035 · 限流

- **状态**：已采纳（2026-10-13，任务 70；Q70a–g 由用户确认，全部按推荐；Q70d 实测后改问一次）
- **日期**：2026-10-13
- **影响**：新增 `app/ratelimit.py`、`Settings` 里的 `rate_limit_*` 配置、错误码 `rate_limited`（HTTP 429 + `Retry-After`）。登录、注册、加入码按 IP 限流，会调模型的接口按用户限流。前端的报错文案带上秒数。

## 背景
- 之前没有任何限流。登录、注册、加入码都能无限次试，可以暴力猜密码和加入码，也能批量注册账号。
- 模型调用只有总量上的约束：成员额度（ADR 0031）、后台每日预算（ADR 0025）、通话分钟。总量管不住突发：脚本一分钟内发几百条消息，会在额度用完前把厂商的速率上限打满，影响同一租户的其他人；自己连接的调用没有额度，只能靠厂商账单发现。
- 部署形态：单个 uvicorn worker（调度器要求，ADR 0025），一台低配服务器。请求路径是浏览器 → Next（`/api` rewrite）→ 后端。后端端口只绑 `127.0.0.1`。

## 决定

### 1. 计数存在进程内存（Q70a）
- 单 worker，进程内的字典就够用，不引入 Redis，也不写 Postgres。
- 重启后计数清零，可以接受：限流是挡突发，不是记账。
- 以后要多 worker 或多实例，再把存储换成 Redis，接口不变。

### 2. 算法：滑动日志
- 每个 key（档名 + 主体）一个时间戳队列，最多存 `limit` 个。请求进来先丢掉窗口外的时间戳，剩下的不足 `limit` 才放行并记下当前时间。
- 超限时，`Retry-After` = 队列里最早的时间戳 + 窗口 − 现在，向上取整到秒，至少 1。
- 比固定窗口准，没有窗口边界上翻倍的问题。内存是 key 数 × limit，量级很小。没有新请求的 key 会被定期清掉。
- 进程内是单线程的 asyncio，检查和记录之间没有 await，所以不用加锁。

### 3. 各档与默认值（Q70b、Q70c、Q70e）
配置写成 `次数/时长`，时长单位是 `s` / `m` / `h`。每档一个环境变量 `RATE_LIMIT_<档名>`，都可以在 `.env` 里改。

| 档 | 默认 | 主体 | 接口 |
|---|---|---|---|
| `login` | 10/15m | IP + 邮箱 | `/auth/login`、`/auth/token`：只数失败，登录成功就清掉这个 key |
| `login_ip` | 50/15m | IP | 同上，只数失败，防止一个 IP 换着邮箱试 |
| `login_email` | 30/15m | 邮箱 | 同上，只数失败，不看 IP（见 §4） |
| `signup` | 10/1h | IP | `/auth/register`、`/org/join/preview`、`/org/join` |
| `chat` | 20/1m | 用户 | 发消息、开场白、聊天附件、消息翻译、口语开始 / 结束 / 纠错、阅读辅导、每次通话连接 |
| `generate` | 10/1m | 用户 | 练习出题和判分、阅读改写 / 开读 / 交答案、写作提交、例句生成、手动加记忆 |
| `tts` | 60/1m | 用户 | `/speech/tts` |
| `asr` | 30/1m | 用户 | 跟读评测、语音附件转写 |

- 只读写数据库的接口不限。管理员的测试连接也不限，它本来就只有管理员能点。后台任务也不限，它们已经有每日预算。
- 登录只数失败：正常用户在多台设备上登录不会被误限。三档都看失败次数，任何一档超限就返回 429。超限时直接返回 429，不再校验密码，所以超限期间也试不出密码对不对。
- 限流和额度分工：限流挡单位时间内的突发和暴力尝试，额度管一天、一个月的总量。两者互不替代。

### 4. 客户端 IP（Q70d）
- 取 `X-Forwarded-For` 最右一项，没有这个头时用 `request.client.host`。
- 实测 Next 16 的 rewrite 不会在 `X-Forwarded-For` 后面追加 IP：只有请求里没有这个头时，才用 socket 地址补上（`next/dist/server/base-server.js`，`??=`）。所以浏览器如果自带这个头，Next 会原样转给后端。Next 直接对公网时，按 IP 的档（`login`、`login_ip`、`signup`）可以靠伪造这个头绕过。
- **公网部署必须在 Next 前面放一层会覆盖 `X-Forwarded-For` 的反向代理。** Caddy 默认丢掉不受信来源带的这个头，换成真实 IP，任务 71 的 prod 覆盖会带上 Caddy。经过 Caddy 和 Next 之后，后端看到的只有一项，就是真实 IP。
- `login_email` 不看 IP，就算 IP 被伪造，也限住了对单个账号的暴力尝试。代价是：攻击者可以故意输错，让某个账号 15 分钟内登不上。这个代价可以接受，而且 30 次的门槛远高于正常用户输错的次数。
- 按用户的档不看 IP，不受影响。
- 后端端口只绑 `127.0.0.1`，外部绕过 Next 直连后端、伪造这个头的路走不通。

### 5. 返回与前端
- HTTP 返回 429，错误码 `rate_limited`，带 `Retry-After` 头（秒）。
- 通话 WebSocket 已经 accept 之后，沿用现有的 `ended / refused` 消息，`code: "rate_limited"`，并附 `retry_after`。
- 前端的 `ApiError` 带上 `retryAfter`（普通请求、SSE、服务端请求都读）。`errors.rate_limited` 文案是“操作太频繁，{seconds} 秒后再试”，经 `useErrorMessage` 显示，现有的报错位置都会自动生效（Q70f）。不加全局弹窗、自动倒计时和自动重试。

### 6. 开关（Q70g）
- `RATE_LIMIT_ENABLED` 默认开。只有自己用的自部署可以关掉。
- 测试：pytest 每个测试前清空计数；E2E 的后端把 `signup` 调高，免得测试自己被限。

## 取舍
- 进程内计数不跨进程，重启就清零。单 worker 的约束是调度器定的，这里没有引入新约束。
- 不加反代时，按 IP 的档可以被绕过（§4）。`login_email` 兜住了暴力猜密码，批量注册和猜加入码在这种部署下挡不住，所以部署文档要求公网部署必须加反代。
- 不做按租户的总限流：成员用主账号连接时已经有额度，自己的连接由自己付钱。
