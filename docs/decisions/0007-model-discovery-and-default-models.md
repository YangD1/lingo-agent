# 0007 · 模型发现、连接默认模型与路由兜底

- **状态**：已采纳
- **日期**：2026-09-28
- **影响**：修订 ADR 0004 §2（路由解析多了最后一层兜底）和 §6（新增接口、测试接口的 `model` 变为可选；§4 起连接名称可以修改）。ADR 0004 的其他内容不变。

## 背景
按 ADR 0004 实现的设置页（P0 任务 10.6），用户第一次实际使用时就卡住了：

1. **没法测试**：测试按钮必须先手填一个模型名。自定义连接（比如 OpenAI 兼容的中转站）没有预设模型可以预填，用户也不知道该填什么。
2. **建好连接也不能聊天**：YAML 的默认路由按连接**名**去匹配（`deepseek:…`、`openai:…`）。用户给中转站起的名字（比如 `dd`）不在默认路由里，整条链都匹配不上，接口返回 409 `no_llm_configured`。要让它能用，用户得自己知道中转站有哪些模型，再手写 `dd:<模型>` 形式的路由。

对普通用户来说，这两件事都要求了解太多内部细节。

## 决定

### 1. 模型发现
- 各厂商都提供“列出可用模型”的接口：OpenAI、DeepSeek、通义兼容模式、Ollama 以及各种 OpenAI 兼容中转是 `GET {base_url}/models`（Bearer 认证，返回 `data[].id`）；Anthropic 是 `GET {base_url}/v1/models`（`x-api-key` + `anthropic-version` 请求头，按 `has_more` / `last_id` 翻页）。调用这个接口**不消耗 token**，并且能顺带验证 key 是否有效。
- 实现放在 provider 层（`app/providers/model_catalog.py`），和真实模型调用**用同一个 SSRF 防护 HTTP 客户端**（ADR 0004 §4），业务代码不直接调用厂商。
- 按模型 id 做简单归类：`chat` / `embedding` / `other`（语音、图像、审核、rerank、realtime 等）。设置页的对话模型下拉框只列 `chat`。只看名字做归类，允许有误判：最坏的情况只是下拉框里多出一个不能聊天的选项，测试时会报错。
- 结果按连接缓存 10 分钟，缓存键包含连接的 `updated_at`，所以换 key 或改地址后会重新拉取。
- 新接口：`GET /tenant/connections/{id}/models`。拉取失败时返回错误码 `model_list_failed`，附带厂商给出的原因（比如 401）。

### 2. 连接的默认模型
- `provider_connections` 新增可为空的列 `default_model`，创建或修改连接时可以设置。
- 前端流程：保存连接 → 自动拉取模型列表（成功就说明 key 有效）→ 选一个默认对话模型。推荐项的规则：预设连接用预设的第一个模型；其他情况优先选 YAML 默认路由里出现过的模型，没有就取第一个 `chat` 模型。拉取失败时允许手填模型名。
- 测试接口 `POST /tenant/connections/{id}/test` 的 `model` 改为可选，不传就用 `default_model`；两者都没有时返回 422。

### 3. 路由解析：增加一层兜底
某个租户的某个 `llm` 任务，按下面的顺序找模型：
1. 租户对这个任务的手动路由（`tenant_model_routes`）；
2. YAML 中这个任务的路由，没有就用 YAML 的 `default` 路由。只保留租户已有、已启用、key 能解密的连接；
3. **新增**：前两层一个可用模型都匹配不上时，按连接的**创建顺序**，依次使用各连接的 `default_model`，组成降级链。

只有在前两层完全匹配不上时才用第 3 层，不会插到前两层的后面去。这样部署方在 YAML 里设计的路由（比如“便宜模型做分类”）在有匹配连接时照常生效，行为可以预期。`embedding` 这一节不走第 3 层，因为默认模型只针对对话。

`GET /tenant/routes` 为每个任务返回**实际生效**的模型链，以及它来自哪一层（`override` / `default` / `auto`）。设置页据此显示“现在用的是哪个模型”，用户不用去推断解析规则。

### 4. 连接的所有字段都可以修改（2026-09-28 补充，用户实测反馈）
原来连接的名称不能修改（ADR 0004：路由按名称引用连接），API 类型也不能修改，写错了只能删掉重建，重建后还得重新配路由。现在 `PATCH /tenant/connections/{id}` 支持修改 `name`、`kind`、`base_url`、`api_key`、`default_model`：
- **改名**：格式校验和创建时相同，重名返回 409 `connection_name_taken`。在**同一个事务里**把该租户所有手动路由（`tenant_model_routes`）中的 `旧名:模型` 改写为 `新名:模型`，所以改名不会让路由失效。`llm_usage` 里的历史记录保留当时的名称，不改写，因为它是事实记录。
- **改 API 类型**：改成必须带 key 的类型（deepseek、anthropic、openai）时，连接必须已经有 key，或者在同一个请求里提供 key。
- 名称、类型、地址、key 中任意一项变了，都清掉上次的测试结果。模型列表缓存和模型实例缓存的键里带着 `updated_at`，会自然失效。
- key 的密文绑定的是租户 id 和连接 id，不是名称，所以改名不需要重新加密。
- **副作用**：YAML 默认路由按名称匹配连接，所以从预设建的连接改名后就匹配不上了，会退到第 3 层（用这个连接的默认模型）；设置页也会重新把这个预设列为可添加。前端在编辑表单里提示这一点。

## 取舍
- **先保存连接，再拉模型列表**，而不是保存前先拿 key 去试：这样 key 只经过一次“加密入库”的流程，不需要再开一个接收明文 key 的接口。代价是 key 填错时，连接会先存下来（卡片上显示错误），用户可以替换 key 或者删掉。
- **兜底只看各连接的默认模型，不猜最好的模型**：只看名字没法可靠判断哪个模型最好。选模型交给用户在创建连接时做一次，系统不替他做。
- **不把第 3 层接在前两层的后面**：接上去降级链会更长，但部署方的路由就不再是“写什么用什么”了。需要多个连接互为备用的用户，可以在设置页用下拉框显式编辑路由。
