# 0048 · 出题流式写整组，写完一道就审一道，过审的题先显示

- **状态**：已采纳（2026-10-16，任务 89.3–89.4；方向由用户选定：一次出整组题，渲染分出）
- **日期**：2026-10-16
- **影响**：修订 ADR 0021 §3（出题图）、ADR 0044 §4（测验卡片等整组出完）。`providers/llm.py` 新增 `astream_structured`；`agents/exercise_graph.py` 的出题改成流式调用，审题按题进行；`rules.yaml` 的 `practice` 一节新增 `parallel_calls`；过审的题立刻存库；题组在 `generating` 时也能作答；`/practice/sets/{id}` 新增 `planned`；练习页和测验卡片先显示已就绪的题。无迁移。

## 背景
- 实测（任务 89.1，百炼 qwen-plus，测验 5 题）：从卡片出现到能作答约 57 秒。其中出题一次调用 30 秒（输出 1319 token），审题一次调用 17 秒，重写被拒的题 7 秒。开发库里用 DeepSeek-V4-Flash 出题平均 33 秒，审题约 15 秒。sub2api `gpt-6-sol` 默认思考强度下，思考约 27 秒后才开始写题。
- 慢在两处：推理模型先思考；流程上要整组写完、整组审完，前端还要等整组离开 `generating` 才显示第一题。一次结构化输出的耗时大致和输出长度成正比。
- 用户的设想是“预设组件、AI 只填内容”。题型组件和数据结构本来就是预设的（ADR 0021 §2、任务 86.9），所以这次改的是流程，不是题型。

## 决定

### 1. 一次流式出题，写完一道就审一道
- 每一轮对所有还没完成的题位发**一次**出题调用，用流式结构化输出（`astream_structured`：强制工具调用，参数逐块到达）。schema 里每个题位一个 `item_<位置>` 字段，模型按顺序写；某个字段之后出现了下一个字段（或调用结束），这道题就写完了。
- 写完的题立刻交给代码校验（`drafts.to_body`），通过的单独送审（`critic_messages` 只传这一道），同时进行的审题不超过 `practice.parallel_calls`（4）。`drafts.judge` 判定，过审的立刻存库（§2）。
- 被拒或校验不过的题带着原因进入下一轮，下一轮仍是一次调用写所有这些题，最多 `1 + practice.max_regenerations` 轮，和以前一样。
- 等待预算（任务 49.3）按轮判断：按上一轮的耗时估算，开新一轮会超出预算就不开，没完成的题位交给题库补。
- 出题调用中途失败：已经写完的题照常审，其余题位交给题库，不再开新的一轮。某道题的审题失败只结束这一道。`NoModelConfiguredError`（没配模型、额度用完）让所有题位都不再开新调用。
- 阶段（`stage`）：第一轮是 `generating`，之后是 `rewriting`，补题库时是 `filling`。审题和出题同时进行，所以不再上报 `reviewing`。

### 2. 过审的题立刻存库，题组仍是 `generating`
- 一道题过审后，马上写一行 `exercises`（`status = ok`）。题组状态不变，接口照常返回已存的题，按 `position` 排序，中间可能有空缺（还没出完的题位）。
- 全部题位结束后，`fill` 用题库补空缺，`save_result` 只插入还没存过的题（按 `position` 去重）、被拒的草稿，然后改题组状态。
- 进程中途退出时：已经存了的题保留，题组照旧被服务标成 `failed`（ADR 0021 §3）。

### 3. 出题过程中就能作答
- `generating` 的题组里已存的题可以作答（`answer.OPEN_SET` 加上 `generating`）。
- 第一次作答时记录“作答前的掌握度”（Q35c）。这时还有题没出来，所以按计划里的语法点（`kc_plan`）记，而不是按已有的题记。题组状态仍是 `generating`。
- 出题结束时：
  - 已经开始作答的题组（有 `mastery_before`）变成 `in_progress`，否则变成 `ready`。题库补进来的、计划外的语法点（`wider_kcs`）在这时补记作答前的掌握度：这组题还没碰过它们，此时的值就是作答前的值。
  - 如果这时所有题都已作答，题组直接变成 `done`。练习页的“提前生成下一组”也在这里触发（以前只在作答接口里触发）。
- 题太少（少于 `min_items`）时：还没开始作答就照旧 `failed`；已经开始作答的不判失败，用已有的题收尾。学习者已经在做的题不应该消失。

### 4. 接口
- `SetOut.planned`：计划的题数（`kc_plan` 的长度；计划排好之前是 0）。出题过程中，前端用它显示“第 n / 共 N 题”。出完以后，以实际题数为准（被丢掉的题位会让题数变少）。

### 5. 前端
- 练习页、测验卡片：只要有一道已就绪、还没作答的题就显示出来，`generating` 时继续轮询。作答完已显示的题、后面的还在出时，显示“正在出下一题”。
- 题不一定按题位顺序就绪（后面的题可能先过审），所以当前题按 id 记；题号按作答顺序编，出题中总数用 `planned`。轮询时正在看的题（包括刚答完、正在看讲解的）保持不动。
- 测验卡片的小结、练习页的总结只在题组离开 `generating`、而且没有待作答的题时出现。

### 6. 代价与实测
- 出题仍是一次调用，系统提示和学习者信息只发一次；每道题单独审，审题的输入比整组审多一些（每次都带审题说明和学习者信息），输出变短（实测单题约 140 token）。
- 实测（任务 89.3b，sub2api `gpt-6-sol`，测验 5 题，思考强度 low）：第一道题过审 10–12 秒，整组 19–21 秒。思考强度默认时，光是思考就要约 27 秒才开始出字，所以出题、审题的默认思考强度设为 low（任务 89.5）。

## 考虑过的方案
- **每道题单独调用出题、并行**（任务 89.3 第一版，已实现后又改掉）：第一道题出得也快，但每道题都要重发系统提示和学习者信息（5 题测验输入约 6.6k → 18k token），题与题之间看不到彼此，难以避免重复；用户更倾向一次出整组、只是分开显示。
- **只换快模型 + 流式 + 等待动画，不改流程**：题必须先过审才能给学习者（CLAUDE.md），整组写完才开始审，学习者看到的仍是一段很长的等待。
- **整组写完后再按题并行审**：比原来快，但第一道题要等整组写完。作为流式拿不到逐块参数时的退路，现在的实现自然覆盖（流结束时把没处理的题一次送审）。

## 后果
- 轮次在 `produce` 节点内部推进，图只剩 `produce → fill → save` 三个节点。
- provider 层新增 `astream_structured`（流式结构化输出，强制工具调用，出第一块前失败才换下一个模型），以后别的长结构化输出也可以边写边用。
- 被拒、校验不过的原因仍然写进 `exercises.critic`（被拒的题）和日志，评估集照旧可以用。

## 补充：时间预算封顶、出题中途卡住只续写剩下的（2026-10-18，任务 101.4e，ADR 0056）
- **学习者在等的那组按 `wait_budget_seconds` 封顶**：原来只在开新一轮前检查，进行中的出题、审题调用会一直等到结束（任务 101.1 见过 213 秒）。现在 `produce` 开始时定下截止时间，出题流和每次审题都在截止时间内进行；到点就取消还在进行的调用。已过审、已发布的题留下，被取消的审题和没写完的位置由题库补，不算模型故障（不记 `model_error`）。存题（`publish`）不在截止范围内，不会被取消到一半。后台预生成没有时间预算，不受影响。被取消的调用由用量记录器记成 `cancelled`。
- **出题流中途卡住**（provider 层抛 `CallStalledError`，ADR 0056 §3）：卡住前写完的题照常审；最后一道可能只写了一半，不用。只为没写完的位置重发一次出题，占这一组的重试预算（`SET_RETRIES = 10`，出题和审题共用），不占重写轮数。预算用完就不再重发，剩下的位置由题库补。
